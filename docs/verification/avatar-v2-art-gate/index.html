Phase 1 audit · why the current system repeats faces

Four shapes also act as identitiesportraitPlan.ts selects head-{face}-{stage}. Every adult with the same face index uses the same eyes, brows, nose and mouth. Four contours cannot provide sixteen distinct facial identities. CreationElements.tsx supplies sixteen different trait combinations, but not sixteen facial bases.
Childlike proportions are in the artworkThe current head sheets use large round eyes, broad white sclera, short facial planes and similarly smiling mouths. Extra skin/hair combinations cannot create the original reference's smaller dark eyes, mature jaw shapes or individual expressions. The source head artwork needs replacing.
RGB classification flattens detailtools/build-portrait-art.py classifies skin with r > 130, channel differences and a percentile reference, then replaces skin with a flat mask and three black shadow opacity levels. Hair shading is reconstructed from a smoothed red channel. This throws away authored hue, subtle cel highlights and some expressive line transitions.
Hair is fitted and split approximatelyThe runtime stretches wigs horizontally within 0.93–1.17×. Foreground/rear separation uses a fixed rectangular region (y > 224, 145 < x < 367). It is not an independently authored registered front/rear pair. It can obscure or alter the illustration's intended overlap and line quality.
Four clothes and coupled controlsThe current outfit is (face + skin + hair * 3 + hairColor * 2) % 4. Changing hair colour jumps to a different outfit; changing hairstyle or skin can also change clothing. This violates the V2 control-independence requirement. Clothing needs its own stable identity or saved/fallback outfit choice.
No distinct facial-identity fieldThe appearance schema stores only face, skin, hair, hairColor. The next implementation must separate facial identity from the four face-shape controls and mutable hair/skin choices. Any added identity/outfit data needs backwards-compatible validation and a deterministic migration or fallback based on stable person identity, without gameplay randomness.
What can be reusedThe shared CharacterPortrait entry point, all existing portrait consumers, accessibility semantics, scalar memoization, eight age-stage boundaries, local asset bundling, six/eight/five/four option counts, and existing save/UI test journeys remain useful. portraitImages.ts is a static registry pattern; its current illustration entries are replaceable.
What needs replacement after approvalThe four generic facial bases, repetitive facial features, four-outfit catalogue, mutable-trait outfit hash, RGB-derived feature/shadow masks and approximate front/back hair splitting. Preserve the approved full-colour illustration quality with individually authored registered components or a small set of curated variants where modularity would degrade it.
UI and scopeapp/appearance.tsx already preserves other appearance properties when a control changes; its screen layout and controls can remain. src/ui/components.tsx aliases Portrait = CharacterPortrait, so a later compatible renderer replacement reaches creation, Life, profiles, family, NPCs and legacy together. No production code, save schema, gameplay or UI is changed in this artwork gate.
