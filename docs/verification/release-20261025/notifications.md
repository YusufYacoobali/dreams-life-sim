# Daily reminder audit — 25 October 2026

Source review fixed permission/status gaps, closed-app clock handling and a stale Settings message. This is source/configuration evidence; this audit did not run an installed Android/iOS delivery test.

| Finding | Evidence and resulting behavior |
| --- | --- |
| Android channel disabled independently of app permission | [Adapter](../../../src/notifications/expoReminderAdapter.ts) now checks the existing `dreams-daily-reminders` channel's importance after app permission is granted. A blocked channel reports the specific Settings action, cancels only owned pending requests, and is never reset or recreated to bypass the user's choice. A later foreground refresh restores scheduling after the user allows that channel. |
| iOS authorization with every visible destination disabled | Authorization alone previously appeared sufficient. The adapter now reports denial when alert, Notification Centre and Lock Screen destinations are all explicitly disabled. Provisional/ephemeral authorization with quiet Notification Centre delivery still works. Unknown/null destination values are not treated as denial. |
| Closed-app Android timezone/clock changes | Installed `expo-notifications` 57 source schedules each next weekly occurrence as an RTC alarm (`ExpoSchedulingDelegate.kt`), and its manifest/`NotificationsService.SETUP_ACTIONS` only restores on reboot/update. It does not handle `TIME_SET`/`TIMEZONE_CHANGED`. The [existing config plugin](../../../plugins/withLocalNotifications.cjs) now generates a private [clock receiver](../../../plugins/templates/DreamsReminderClockReceiver.kt) to re-arm only already-saved Dreams reminder IDs on those broadcasts. No new permission is added. This requires a newly generated native build. |
| Cancellation concurrent with clock re-arming | Expo's `NotificationsService.doWork` sends broadcasts and `onReceive` launches a thread per event; forwarding through that service is not a serialized queue. Calling `ExpoSchedulingDelegate.scheduleNotification` on an earlier snapshot would save a request again after cancellation. The clock receiver now re-reads each current owned record, skips missing/unschedulable records, and changes only its existing alarm through the SDK's public PendingIntent API. It never saves/schedules a notification request or writes the notification store. If cancellation races after the read, an obsolete alarm cannot restore its removed record; Expo's `triggerNotification` reads that store at delivery and drops the missing request. |
| Stale denial after returning from OS Settings | [DailyReminderSettings](../../../src/ui/DailyReminderSettings.tsx) clears its earlier permission-denied notice when foreground reconciliation actually transitions to `scheduled`. This does not write preferences or life data. |

The remaining traced paths preserve their existing behavior:

- Fresh preferences default reminders on at 19:00; historical omitted fields and explicit opt-outs remain off. Settings persistence is separate from lives. As requested in the startup follow-up, automatic permission is attempted when the app opens after readable enabled preferences load, while foregrounded, and only for undetermined permission. It does not wait for a life to exist or begin. Existing granted/denied permissions are not automatically requested again, and the request does not repeat when returning from the OS dialog. Explicit enable obtains permission before committing the preference. Failed SQLite writes do not change the schedule.
- [The planner](../../../src/notifications/reminderPlan.ts) uses seven weekly local-calendar slots with stable weekday IDs, not 24-hour intervals or an expiring dated batch. It validates 00:00–23:59. Zone name plus current UTC offset is part of the reconciliation metadata. Message banks rotate when the app reconciles in a new local week; without reopening, existing weekly messages continue.
- [The service](../../../src/notifications/dailyReminders.ts) serializes permission/schedule changes, snapshots settings, re-reads native pending requests on every reconcile, repairs duplicates/partial failures, and preserves other features' requests. Disable/revocation removes owned requests only. The conservative 64-request capacity gate does not evict unrelated requests.
- [The root host](../../../src/ui/AppReminders.tsx) reconciles after readable preferences load, on saved enable/time changes and on foreground. Cleanup and latest-preference checks prevent an outstanding permission prompt from re-enabling a later opt-out. [Status](../../../src/state/reminderStatus.ts) accepts only the newest refresh result.
- Tap handling accepts only the default action on an owned reminder with the expected `owner` and `action`. Live and initial responses are deduplicated within the running service. It opens `/`, the ordinary Welcome/Continue screen, without selecting a saved life, advancing time or dispatching a game command. Foreign actions and URLs are ignored. Adapter/response failure does not block startup.
- Android channel creation precedes the first permission request and requests no sound, vibration or badge. Existing channel settings are preserved. The local-only plugin still removes the APNs entitlement and disables remote-notification background mode; no push registration/token/server is used. Expo Go/web are rejected before importing the native notification module.

## Remaining release evidence

An installed final build is still needed to establish Android 13+ permission UI/channel behavior, actual scheduled delivery after process death/reboot, closed-app clock/timezone re-arming and cold-tap navigation, plus iOS permission/delivery behavior. The generated Kotlin receiver has not yet been compiled or exercised on Android by this audit. Source inspection alone is not that acceptance.

Exact-to-the-minute delivery is not guaranteed: Expo's Android scheduler uses an inexact idle alarm when exact-alarm access is unavailable, and OS focus/battery policies still apply. Weekly triggers delegate skipped/repeated DST wall times to the native calendar/OS; no simulated DST result is claimed. iOS weekly `DateComponents` omit a fixed timezone. Android's next trigger uses the current default calendar and the new receiver handles later clock/zone changes.

Peer source review confirms the alarm-only receiver uses the installed SDK's public APIs and cannot re-persist a cancelled request. Native alarm and stored-time changes are not atomic: a clock broadcast overlapping a saved reminder-time edit can race the next alarm time. This is not a claim of atomic native scheduling or an installed concurrency test.

There is no foreground notification handler, so the SDK suppresses presentation while the game is open; foregrounding still refreshes the pending schedule. The dedicated white heart notification icon replaces the opaque launcher fallback. Final native generation verifies all five transparent white density variants; installed rendering remains a device check.

Root verification passed all three named plugin cases using the direct Node invocation above. The final generated receiver also compiled with Kotlin 2.1.20 against Android API 36, the actual Expo Notifications 57.0.23 AAR and AndroidX Core 1.17.0. This checks the receiver's APIs and bytecode generation; it does not compile the whole app or establish device delivery.
